# Соглашения и правила разработки проекта

Этот файл фиксирует правила оформления кода, Git flow и другие аспекты разработки в монолите FilmHelperApp.

Документ пополняется по мере появления договорённостей: каждое новое правило добавляется
отдельным пронумерованным разделом.

---

## 1. Двойной отступ между группами членов класса

### Правило

Внутри тела класса члены группируются, и группы отделяются друг от друга **двумя пустыми
строками**. Внутри одной группы — **одна пустая строка**.

Группа — это набор членов класса, у которых совпадают:

1. вид члена класса (константа / свойство / метод);
2. спецификатор доступа (`public` / `protected` / `private`).

Отсюда два следствия:

- **Между разными спецификаторами доступа** одного и того же вида члена
  (`public` -> `protected` -> `private` константы, свойства, методы) — две пустые строки.
- **Между разными видами членов класса** (константы -> свойства -> методы) — две пустые строки.

Порядок объявления: сначала константы, затем свойства, затем методы. Внутри каждого вида —
от более открытого к более закрытому: `public`, `protected`, `private`.

### Зачем

Границы секций видны сразу, без чтения модификаторов построчно. При беглом просмотре класса
понятно, где заканчивается его публичный контракт и начинается внутренняя кухня.

### Правильно

```php
final class TitleImporter
{
    public const int DEFAULT_LIMIT = 50;
    public const string CACHE_PREFIX = 'import:title:';


    private const int MAX_ATTEMPTS = 3;


    public readonly ProviderSource $source;


    private array $buffer = [];
    private ?ProviderException $failure = null;


    public function __construct(private readonly ProviderClientInterface $client)
    {
        $this->source = $client->source();
    }

    public function import(int $limit = self::DEFAULT_LIMIT): int
    {
        // ...
    }


    protected function shouldRetry(ProviderException $exception): bool
    {
        // ...
    }


    private function flush(): void
    {
        // ...
    }
}
```

### Частные случаи

- Первый член класса пишется сразу после `{`, пустая строка перед ним не ставится.
  Перед закрывающей `}` пустой строки тоже нет.
- Если группа состоит из одного члена — правило не меняется: две пустые строки всё равно
  отделяют её от соседней группы.
- Если какого-то вида членов в классе нет (например, нет констант), лишние пустые строки
  не появляются: правило работает только между реально существующими группами.
- Продвинутые (promoted) свойства конструктора отдельной группой не считаются — они часть
  сигнатуры конструктора, то есть часть группы методов.
- PHPDoc-блок и атрибуты принадлежат своему члену класса и пишутся вплотную к нему.
  Пустые строки ставятся **перед** блоком документации, а не между ним и сигнатурой:

  ```php
  public function failWith(ProviderException $exception, int $afterItems = 0): void
  {
      // ...
  }


  /** @return list<ProviderTitle> */
  private static function defaultFixtures(): array
  {
      // ...
  }
  ```

- `static` сам по себе новую группу не создаёт: группировка идёт по виду члена и
  спецификатору доступа. `public static` и `public` методы лежат в одной группе.
- Правило распространяется на классы, абстрактные классы, трейты и enum'ы. В интерфейсах,
  где все члены публичны, группы обычно две — константы и методы, и они разделяются двумя
  пустыми строками.

## 2. Выравнивание параметров в многострочном списке

### Правило

Если список параметров разбит на несколько строк, имена переменных выравниваются в одну
колонку. Строка параметра читается как три колонки:

```text
<спецификатор доступа>  <тип>  <$имя>
```

Ширина колонки типа считается по самому длинному типу в списке и добивается пробелами,
чтобы все `$имена` начинались с одной позиции. Недопустимо писать «спецификатор, тип и
сразу переменную» — тогда имена разъезжаются по длине соседних типов.

Эталон — конструктор [ProviderTitle](../app/Domain/Import/ValueObjects/ProviderTitle.php).

### Зачем

Многострочный список параметров — это, по сути, описание набора полей. В виде таблицы он
читается за один взгляд: слева видно состав, справа — типы. Nullable-типы (`?string`)
перестают теряться в тексте, а при добавлении поля сразу видно, что колонка «поехала» и
блок нужно переформатировать.

### Правильно

```php
final readonly class ProviderTitle
{
    public function __construct(
        public ProviderSource $source,
        public string         $externalId,
        public ?string        $titleRu,
        public ?string        $titleEn,
        public ?string        $description,
        public array          $genres,
        public ?int           $year,
        public ?int           $durationMinutes,
        public ?float         $rating,
        public ?string        $posterUrl,
        public ?string        $bannerUrl,
        public string         $type,
        public string         $status,
    ) {
        // ...
    }
}
```

### Частные случаи

- Каждый параметр многострочного списка пишется на своей строке, в конце — замыкающая
  запятая.
- Однострочная сигнатура не выравнивается: там один пробел между типом и именем —
  `pubilic function mport(int $limit = self::DEFAULT_LIMIT): int`.
- Правило работает и для обычных (не promoted) параметров: тогда колонка спецификаторов
  просто пуста, а выравниваются `$имена` относительно колонки типов.
- Значения по умолчанию не выравниваются: `=` пишется сразу после имени через один пробел.
- Атрибуты параметра (`#[...]`) выносятся на отдельную строку над параметром и в расчёте
  колонок не участвуют.
- Аргументы при **вызове** (в том числе именованные) не выравниваются — правило касается
  только объявления параметров:

  ```php
  new ProviderTitle(
      source: ProviderSource::Mock,
      externalId: '5114',
      titleRu: 'Стальной алхимик: Братство',
  );
  ```

- Добавление параметра с более длинным типом требует переформатирования всего блока.
  Это ожидаемая цена правила: такой коммит нормален, отдельно его выделять не нужно.
- Блоки объявления свойств и констант класса (см. правило 1) выравнивать не требуется.
