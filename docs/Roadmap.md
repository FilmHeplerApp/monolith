# Roadmap разработки FilmHelperApp

Документ описывает полный список задач по реализации проекта в порядке выполнения.
Источник требований — [TZ.md](TZ.md). Правила написания кода — [How_infrastructure_works.md](How_infrastructure_works.md).

## Как пользоваться документом

- Одна задача = одна ветка = один PR. Названия веток даны в описании задачи.
- Формат коммита сохраняем текущий: `<branch_name>. <краткое описание>`.
- Каждая задача содержит: зачем она нужна, состав работ и критерии готовности (DoD).
- План живой: по ходу разработки задачи можно дробить, объединять и переставлять.
  Единственное, что важно сохранять — порядок этапов.

## Логика порядка этапов

1. Сначала закрываем **всё, что не требует оплаты внешних сервисов**: каталог, импорт на статических
   данных, пользователи, библиотека, подписки на sandbox-шлюзе, рекомендации на локальных эмбеддингах.
2. Затем **frontend** под уже готовый и задокументированный backend.
3. И только в конце — **платные интеграции**: реальные API поставщиков, embedding-модель,
   платёжный провайдер, CDN, push.

Ключевая идея этапа 1: собрать полный флоу `поставщик → фильтрация → валидация → БД`
на статическом датасете. Это даёт рабочий каталог без единого запроса во внешний API
и разблокирует все последующие этапы.

## Принятые архитектурные решения

Решения зафиксированы и учтены в задачах ниже. Менять их по ходу можно, но каждое затрагивает
несколько задач сразу.

### Р-1. Монолит не занимается агрегацией

Весь сбор данных у поставщиков — ответственность **отдельного сервиса-агрегатора**.
В монолите не остаётся ни одного исходящего запроса к API поставщиков.

Разделение ответственности:

```text
Агрегатор (асинхронно, вне монолита)          Монолит
─────────────────────────────────────         ────────────────────────────
запрос к API поставщика                       →  приём пачки из очереди
фильтрация и нормализация                     →  upsert в каталог
сжатие изображений                            →  запись import_runs
выгрузка изображений в хранилище              →  генерация эмбеддингов
формирование готовой к сохранению пачки
отправка пачки в очередь
```

Монолит остаётся владельцем своей БД: писать в неё может только он сам. Агрегатор отдаёт
готовые к сохранению данные в очередь, монолит разбирает их отдельным воркером Horizon
на выделенной очереди — то есть вне процессов, обслуживающих пользователей.

**Последствие:** ветка `abstract_provider_clients` написана в монолите и должна переехать
в репозиторий агрегатора. Код изолированный (контракт, VO, enum, исключения, mock-клиент,
тесты — без зависимостей от внутренностей монолита), поэтому перенос дешёвый.

### Р-2. Аутентификация на JWT

Access-токен — подписанный JWT, refresh-токен — запись в БД с ротацией.

JWT не отзывается сам по себе, а ТЗ требует отзыва при logout (6.1.1, сценарий 4),
при смене пароля (6.1.13) и при смене роли (6.2.6). Поэтому в схему сразу закладываем:

- короткий TTL access-токена (5–15 минут), чтобы окно после отзыва было минимальным;
- уникальный `jti` в каждом токене и denylist отозванных `jti` в Redis с TTL до истечения токена;
- refresh-токены в БД с привязкой к устройству, ротацией и отзывом всей цепочки при переиспользовании;
- асимметричную подпись (RS256/EdDSA) — ключи в секретах, публичный ключ переживает ротацию.

### Р-3. Единая таблица библиотеки

Просмотренные, «Буду смотреть» и «Не интересно» живут в одной таблице `user_library`
с полем `status`: `watched`, `watching`, `dropped`, `planned`, `not_interested`.

Уникальность пары `user_id + title_id` на уровне БД автоматически даёт требования ТЗ:
тайтл не может быть одновременно в двух списках, а переносы между списками —
это `UPDATE status`, а не пара «удалить + вставить».

### Р-4. Эталонный поставщик — Shikimori

Выбран из трёх кандидатов по двум критериям: гарантированный набор полей и наличие русских данных.

| Поставщик | Контракт схемы | Русские данные |
| --- | --- | --- |
| Jikan (MyAnimeList) | OpenAPI 3.1, модель Anime с явной nullability | ❌ только `title`, `title_english`, `title_japanese` |
| AniList | GraphQL, строго типизированная интроспектируемая схема | ❌ только `romaji`, `english`, `native` |
| **Shikimori** | **GraphQL (рекомендуемая версия API) + REST v1 с документированными примерами ответов** | ✅ `russian`, `description` на русском, `genres` с русскими названиями, `license_name_ru` |

Решающий фактор — русский язык. ТЗ требует `title_ru`, `description_ru`, `short_plot_ru`
и русские жанры в справочниках, а приложение русскоязычное по приоритету (ТЗ 5.2).
У Jikan и AniList русских полей нет вообще: выбрав любой из них, мы получили бы вечно пустые
`title_ru`/`description_ru` и были бы вынуждены подключать переводчик — то есть платный сервис,
чего мы как раз и избегаем на этом этапе.

По гарантиям схемы Shikimori не уступает: его **GraphQL API** (сам Shikimori рекомендует его
вместо v1/v2) даёт строго типизированную схему с интроспекцией — ровно тот же уровень
гарантий, что у AniList. Более того, в GraphQL набор полей ответа задаёт сам запрос,
поэтому статические фикстуры — это буквально снимок ответа на наш собственный запрос,
и разойтись с реальным форматом они не могут.

**Итог:** фикстуры делаем в формате ответа Shikimori GraphQL на зафиксированный запрос.
REST v1 держим в уме как запасной вариант — там есть документированные примеры ответов.

### Р-5. Эмбеддинги — text-embedding-3-small на 768 измерений

Размерность фиксируется в схеме БД (`vector(768)`) для тайтлов и пользователей.
Целевая модель для T-76 — OpenAI `text-embedding-3-small`.

Модель обучена по схеме Matryoshka Representation Learning, поэтому умеет отдавать вектор
короче родного: параметр `dimensions` принимает любое значение от 256 до 1536, и при укорачивании
качество деградирует плавно, а не обрывом.

**Обязательно:** у модели размерность по умолчанию — **1536**. Запрос без явного
`dimensions: 768` вернёт вектор, который не влезет в схему. Значение задаём в конфиге
и покрываем тестом (см. T-43).

До T-76 работаем на локальной детерминированной реализации той же размерности.
Смена размерности впоследствии = миграция схемы + полная перегенерация всех векторов.

**Риск, требующий решения до T-76:** OpenAI блокирует трафик API из России с июля 2024 года,
а прод по решению Р-9 живёт в Yandex Cloud. Подробности и варианты — в задаче T-76 и разделе «Риски».

### Р-6. Фронтенд — bare React Native

Стек: bare React Native + TypeScript, без Expo.

Причины выбора RN: команда backend-ориентированная, TypeScript ближе, чем Dart; экосистема
свайп-интерфейсов (`react-native-gesture-handler` + `react-native-reanimated`) закрывает
основной сценарий ТЗ 5.2; проще нанимать под доработку.

Причина отказа от Expo: нужны нативные модули, которых в managed-окружении может не быть, —
платёжный SDK ЮKassa (Р-7) и push-провайдер (T-79). Bare сразу даёт полный доступ к нативному
слою и не потребует болезненного `eject` в середине разработки. Цена решения — самостоятельная
настройка сборки под iOS и Android на старте (учтено в T-65).

### Р-7. Платёжная система — ЮKassa

Решение принято окончательно. Поддерживает карты и СБП, умеет рекуррентные списания
по сохранённому способу оплаты (нужно для автопродления по ТЗ 6.1.17), даёт вебхуки
и мобильный SDK.

Интерфейс `PaymentGateway` (T-39) всё равно проектируем абстрактно — это защищает от смены
провайдера, но активно закладываемся на модель ЮKassa: первый платёж с сохранением способа
оплаты → последующие автосписания по `payment_method_id`.

### Р-8. Транспорт между агрегатором и монолитом — Redis + Horizon

Отдельный брокер не заводим. Оба сервиса уже работают на Redis и Horizon, этого достаточно
для объёмов импорта.

Важная деталь реализации: Horizon сериализует job как PHP-объект, поэтому потребитель должен
знать его класс. Чтобы два репозитория не разъехались, контракт (DTO пачки, класс job
и JSON Schema) выносим в **общий composer-пакет**, подключаемый обоими сервисами.
Это же снимает дублирование схемы контракта. Детали — в T-10.

Выделенная очередь `catalog-ingest` в монолите, отдельная от пользовательских задач,
с собственным пулом воркеров Horizon.

### Р-9. Хостинг — Yandex Cloud

Прод целиком в Yandex Cloud: приложение, PostgreSQL с `pgvector`, Redis, объектное хранилище,
CDN, логирование и мониторинг (ТЗ 5.5). Локально всё то же поднимается в Docker с MinIO
вместо Object Storage.

Следствие, влияющее на T-76: исходящий трафик к внешним ИИ-сервисам пойдёт с российских
IP-адресов — см. раздел «Риски».

### Р-10. Пробный период подписки не делаем

ТЗ 7.5 упоминает триал 7–14 дней как рекомендацию, в сценариях он не описан. В объём не берём.

На уровне схемы это ничего не ломает: если триал понадобится позже, он добавляется
как отдельный статус подписки и ветка в сценарии активации, без переделки таблиц.

## T-04. CI: GitHub Actions (линтер + тесты) ⬜

**Ветка:** `ci_lint_and_tests` · **Статус:** ⬜ · **Зависит от:** T-02

Пайплайн, который гоняется на каждый PR и не даёт влить сломанный код. Ставим его как можно раньше,
чтобы все последующие задачи проверялись автоматически.

**Состав работ**

- Workflow `.github/workflows/ci.yml`: установка PHP 8.4, кэш composer, `composer install`.
- Проверка стиля: `laravel/pint --test`.
- Статический анализ: подключить `larastan/larastan`, задать стартовый уровень (5–6) и baseline.
- Тесты: `php artisan test` с сервисами PostgreSQL (`pgvector`) и Redis в CI.
- Отдельный `.env.testing`, миграции в тестовой БД, базовый `TestCase` и фабрики.
- Бейджи статуса в `README.md`, защита ветки `main` (обязательные проверки перед merge).

**Готово, когда**

- PR с ошибкой стиля, статического анализа или падающим тестом не проходит проверки.
- Локально те же проверки запускаются одной командой.

## T-05. Кастомный профайлер ⬜

**Ветка:** `custom_profiler` · **Статус:** ⬜ · **Зависит от:** T-04

Собственный инструмент замера производительности: без него нельзя осмысленно выполнять
требования ТЗ 5.1 (ответ на рекомендацию ≤ 1–2 сек) и этап оптимизации.

**Состав работ**

- Middleware/слушатели, собирающие по запросу: время выполнения, пиковую память,
  количество и время SQL-запросов, обращения к Redis, вызовы внешних HTTP.
- Обёртка для консольных команд и джоб Horizon (импорт, генерация эмбеддингов).
- Вывод: заголовки ответа `X-Profiler-*` в `local`/`dev`, запись в отдельный лог-канал,
  агрегированная сводка по маршрутам.
- Порог-алерты: подсветка запросов дольше N мс и подозрения на N+1 (более N однотипных запросов).
- Полное отключение в production по флагу в `.env`.

**Готово, когда**

- По любому запросу и джобе видно время, память и список SQL-запросов.
- Профайлер выключается конфигом и не влияет на прод.

## T-06. Инфраструктура воркера-агрегатора 🔄

**Ветка:** `aggregator_infrastructure` (репозиторий `../aggregator`) · **Статус:** 🔄 · **ТЗ:** 4.2 · **Решение:** Р-1

Сервис, который целиком забирает на себя работу с поставщиками. По решению Р-1 весь этап 1
(кроме схемы каталога и сохранения) живёт здесь, поэтому инфраструктуру нужно довести
до рабочего состояния до начала этапа 1. Сейчас в репозитории голый скелет Laravel.

**Состав работ**

- Docker-стек по образцу монолита: PHP-FPM, Redis, Horizon, scheduler, Xdebug, объектное хранилище.
- Слои по тому же принципу (`Domain / Application / Infrastructure / Interfaces`),
  памятка по архитектуре в своём `docs/`.
- Свой CI-пайплайн (линтер + статический анализ + тесты) по образцу T-04.
- Общая с монолитом шина: подключение к тому же Redis/брокеру для передачи пачек данных.
- README с описанием запуска и явной границей ответственности: агрегатор не пишет в БД монолита.

**Готово, когда**

- Сервис поднимается локально, выполняет фоновую задачу-заглушку и кладёт сообщение в общую очередь.

**Важно:** боевые запросы к реальным API поставщиков — это T-74/T-75. До них агрегатор работает
на статическом датасете Shikimori, но уже как полноценный отдельный сервис.

# Этап 1. Каталог и импорт на статических данных

Это текущий приоритет. На выходе этапа — наполненная база тайтлов и полностью рабочий,
покрытый тестами конвейер импорта, которому всё равно, откуда пришли данные.

По решению Р-1 этап разнесён по двум репозиториям. В заголовке каждой задачи указано, где она делается:
**[М]** — монолит, **[А]** — агрегатор.

```text
[А] Shikimori (статика) → фильтрация → нормализация → сжатие и выгрузка изображений
                                                              │
                                                       очередь пачек
                                                              │
                                     [М] приём → upsert в каталог → import_runs
```

## T-07. [М] Схема БД каталога ⬜

**Ветка:** `catalog_schema` · **Статус:** ⬜ · **ТЗ:** 7.1.2, 7.1.5–7.1.9, 7.7

Миграции под гибридную EAV-модель каталога. Фундамент для импорта, поиска и рекомендаций.

**Состав работ**

- `content_types` — типы контента (anime, movie, series, k-drama, cartoon).
- `titles` — основные поля: названия ru/en, описания ru/en, short_plot_ru, год, длительность,
  type, status, poster_url, banner_url, rating_avg, rating_count, embedding (`vector(768)`, решение Р-5),
  updated_by (admin/process), флаг неполноты данных, флаг скрытия, last_synced_at, timestamps + soft delete.
- `attribute_definitions` — справочник параметров (genre, mood, tags, target_audience, studios, pace).
- `attribute_options` — допустимые значения для enum-подобных атрибутов.
- `title_attributes` — значения атрибутов тайтла (`value_text`, `value_array`, `value_number`,
  `value_boolean`, `searchable_text`).
- `title_external_ids` — связка `source + external_id → title_id` с уникальным индексом.
- `import_runs` — журнал запусков импорта (status, error_message, titles_count, execution_time, last_sync_at).
- Индексы: уникальность `source + external_id`, GIN по `value_array` и по поисковому тексту,
  индекс под `pgvector` (`ivfflat`/`hnsw`), индексы по type/status/year.

**Готово, когда**

- Миграции применяются и откатываются, схема покрывает раздел 7.1 ТЗ.

## T-08. [М] Модели, доменные объекты и репозитории каталога ⬜

**Ветка:** `catalog_domain` · **Статус:** ⬜ · **Зависит от:** T-07

Программный доступ к каталогу по правилам архитектуры: `Domain` не знает про Eloquent.

**Состав работ**

- Eloquent-модели в `Infrastructure/Persistence/Eloquent/Models` со связями и кастами.
- Доменные сущности и value objects в `Domain/Catalog` (Title, TitleAttributes, ContentType, ExternalId).
- Интерфейсы репозиториев в `Domain/Catalog/Contracts`, реализации — в `Infrastructure/Persistence`.

## T-10. [М+А] Контракт обмена между агрегатором и монолитом ⬜

**Ветка:** `ingest_contract` (общий пакет + обе стороны) · **Статус:** ⬜ · **Зависит от:** T-06, T-07 · **Решения:** Р-1, Р-8

Договор между двумя сервисами. Делается до остальных задач этапа, чтобы обе стороны
разрабатывались параллельно и не переделывались.

**Состав работ**

- Общий composer-пакет `filmhelper/ingest-contract` (отдельный репозиторий или path-репозиторий
  на время разработки): DTO пачки, DTO итога запуска, класс job, JSON Schema, версия контракта.
  Подключается обоими сервисами — так класс job гарантированно совпадает у отправителя
  и получателя, а схема не дублируется в двух местах.
- Формат сообщения-пачки: версия схемы, поставщик, `run_id`, `batch_id`, массив готовых
  к сохранению тайтлов (уже отфильтрованных, нормализованных, с URL загруженных изображений).
- Формат сообщения-итога запуска: статус, счётчики (создано/обновлено/отсеяно/ошибок), время выполнения.
- Транспорт: Horizon поверх общего Redis, выделенная очередь `catalog-ingest` со своим пулом воркеров.
  Требования — идемпотентность по `run_id + batch_id`, ограничение размера пачки (100–500 тайтлов),
  настроенные `tries`, `backoff` и dead letter.
- Версионирование: монолит отвергает пачку с неизвестной версией контракта и пишет это в лог,
  а не падает.
- Тестовые фикстуры сообщений и контрактные тесты в CI обеих сторон.

**Готово, когда**

- Контракт живёт в общем пакете, обе стороны валидируют сообщения по нему.
- Тестовое сообщение доходит от агрегатора до монолита и корректно отвергается при неверной версии.

## T-13. [А] Фильтрация и нормализация данных поставщика ⬜

**Ветка:** `provider_data_filtering` · **Статус:** ⬜ · **Зависит от:** T-12 · **ТЗ:** 6.3.2

Конвейер приведения сырых данных к внутреннему формату. Реализуем как набор отдельных шагов
(pipeline), чтобы правила можно было добавлять и тестировать поштучно.

**Состав работ**

- Первичная фильтрация:
  - отбрасываем тайтлы без русского и английского названия;
  - тайтлы без описания или постера пропускаем дальше, но помечаем флагом неполноты и логируем
    (админ дозаполняет вручную);
  - фильтр по типу контента (на старте — только `anime`);
  - фильтр по году выпуска (порог из конфига, на старте 1990+);
  - фильтр по популярности (рейтинг / количество оценок выше порога).
- Нормализация:
  - очистка HTML и BB-кода Shikimori из описаний, схлопывание пробелов, обрезка до 700–1000 символов;
  - приведение названий к единому виду;
  - маппинг жанров Shikimori на внутренний список приложения (справочник из T-09);
  - маппинг `kind` и `status` на внутренние enum-ы;
  - вычисляемые поля (примерная длительность, статус выхода);
  - выделение атрибутов в структуру под `title_attributes`.
- Дедупликация внутри пачки по `source + external_id`.
- Результат шага — DTO `NormalizedTitle`, соответствующий контракту T-10.
- Журнал отсева: причина отбраковки по каждому тайтлу (в лог + счётчики для итога запуска).
- Все пороги и правила — в конфиге, а не в коде.

**Готово, когда**

- Unit-тесты покрывают каждое правило фильтрации и нормализации отдельно.
- На «грязном» датасете видно, сколько записей прошло и сколько отсеяно с причинами.

## T-14. [А] Сжатие изображений и выгрузка в хранилище ⬜

**Ветка:** `image_processing` · **Статус:** ⬜ · **Зависит от:** T-13 · **ТЗ:** 4.2, 7.2

Постеры и баннеры обрабатываются в агрегаторе: монолит получает уже готовые URL.
Цель сжатия по ТЗ — уменьшение объёма в 3–5 раз.

**Состав работ**

- Интерфейс `ImageCompressor` + реализация на `spatie/image-optimizer` или `intervention/image`
  (нужные бинарники добавляются в Dockerfile агрегатора).
- Пресеты по назначению (`poster`, `banner`), несколько размеров (thumb / card / full),
  конвертация в webp с fallback.
- Валидация входа: максимальный размер, допустимые mime-типы, защита от «бомб».
- Скачивание исходника по URL поставщика с таймаутом, ретраями и ограничением размера.
- Интерфейс `ImageStorage` поверх S3-совместимого диска, схема ключей
  `titles/{source}/{external_id}/{type}/{hash}.{ext}` — устойчивая к повторным импортам.
- Идемпотентность: изображение с таким же хэшем повторно не заливается.
- Graceful degradation: недоступность хранилища не роняет импорт — тайтл уходит в монолит
  без картинки и с флагом неполноты.
- Метрики: исходный и итоговый размер, коэффициент сжатия, время.

**Готово, когда**

- Тест подтверждает сжатие тестового набора в 3–5 раз без визуального брака.
- В пачке для монолита лежат рабочие URL уже загруженных изображений.

**Примечание:** аватары пользователей загружаются в монолит напрямую (T-25), поэтому там нужен
свой минимальный обработчик изображений. Если код начнёт дублироваться — выносим в общий
composer-пакет, но не раньше, чем появится вторая реальная точка использования.

## T-16. [М] Приём и сохранение данных в локальную базу ⬜

**Ветка:** `catalog_ingest` · **Статус:** ⬜ · **Зависит от:** T-10, T-08 · **ТЗ:** 6.3.3

Единственное место, где монолит участвует в импорте: разбирает очередь и пишет в свою БД.
Работает на выделенной очереди Horizon, то есть не конкурирует за ресурсы с пользовательскими запросами.

**Состав работ**

- Воркер-потребитель очереди пачек: валидация по JSON Schema, проверка версии контракта,
  идемпотентность по `run_id + batch_id`.
- Логика сохранения по шагам ТЗ 6.3.3:
  1. поиск записи в `title_external_ids` по паре `source + external_id`;
  2. если найдена — обновляем связанный `title`;
  3. если нет — ищем возможный дубль по названию, году и типу;
  4. дубля нет — создаём новый `title`;
  5. создаём/обновляем `title_external_ids`;
  6. сохраняем атрибуты (жанры, теги, студии) в `title_attributes`;
  7. обновляем `last_synced_at`.
- UPSERT (`INSERT ... ON CONFLICT`) и пакетная запись вместо N запросов на N тайтлов.
- Защита ручных правок: поля с `updated_by = admin` импортом не перетираются.
- Пропавшие у поставщика тайтлы не удаляем; скрытие — только через статус.
- Транзакция на пачку + устойчивость к частичным ошибкам: сбой одного тайтла не роняет пачку,
  проблемные записи уходят в dead letter с причиной.
- Запись итогов в `import_runs` по сообщению о завершении запуска.
- Постановка джобы генерации эмбеддинга для новых и изменённых тайтлов (реализация — T-44).

**Готово, когда**

- Повторная доставка той же пачки не создаёт дублей и не меняет ручные правки.
- Интеграционные тесты на upsert, дедупликацию, идемпотентность и защиту admin-полей зелёные.

## T-17. [М+А] Сквозная проверка флоу импорта на статике ⬜

**Ветка:** `import_e2e_check` · **Статус:** ⬜ · **Зависит от:** T-15, T-16

Контрольная точка этапа: доказываем, что цепочка «получение → обработка и валидация → сохранение в БД»
работает целиком через два сервиса.

**Состав работ**

- Тест на стороне монолита: пачка из фикстуры → воркер → проверка `titles`, `title_attributes`,

- Заметка в `docs/` обоих репозиториев: как запускать импорт и как добавить нового поставщика.

**Готово, когда**

## T-21. Аутентификация: access/refresh, выход, защита от брутфорса ⬜

**Ветка:** `user_authentication` · **Статус:** ⬜ · **Зависит от:** T-20 · **ТЗ:** 6.1.1 (сценарии 2–4) · **Решение:** Р-2

**Состав работ**

- Подключение JWT-библиотеки (`lcobucci/jwt` или `firebase/php-jwt`) и собственный guard.
  Подпись асимметричная (RS256/EdDSA), ключи в секретах, поддержка ротации ключей по `kid`.
- Состав claims: `sub`, `jti`, `iat`, `exp`, `role`, версия токена. TTL access — 5–15 минут.
- Вход по email или логину, проверка пароля, выдача пары access + refresh.
- Refresh-токены в БД с ротацией: при обмене старый помечается использованным, выдаётся новый.
  Повторное использование уже потраченного токена → отзыв всей цепочки (`family_id`) как признак кражи.
- Denylist отозванных `jti` в Redis с TTL до истечения токена — механизм отзыва для logout,
  смены пароля и смены роли.
- Logout: отзыв refresh-токена, добавление `jti` в denylist, очистка пользовательского кэша.
- Middleware проверки: подпись → срок → denylist.
- Защита от брутфорса: 5 неудачных попыток → бан на час, с понятной ошибкой на фронт;
  счётчик в Redis, подсказка про восстановление после 3 попыток.
- Обновление `last_active_at`.

**Готово, когда**

- Полный цикл login → refresh → logout покрыт тестами, бан после 5 попыток работает.
- Отозванный токен перестаёт работать сразу, а не по истечении TTL.
- Тест на повторное использование refresh-токена отзывает всю цепочку.

  пакетная генерация, размерность вектора.
- Локальная реализация без внешних сервисов: детерминированный вектор **768** измерений
  (hashing trick / bag-of-features по жанрам, тегам, настроению, году, типу), нормализация длины.
- Размерность 768 зашита как константа проекта и проверяется тестом на соответствие схеме БД —
  расхождение схемы и модели должно падать в CI, а не в проде. Тест особенно важен из-за того,
  что у целевой модели `text-embedding-3-small` размерность по умолчанию 1536 (Р-5).
- Выбор реализации через `.env`, версия модели сохраняется рядом с вектором.
- Работа с `pgvector`: хранение, косинусное расстояние, индексы (`hnsw` для 768 измерений),
  проверка запросов на плане.
- Кэширование векторов.

**Готово, когда**

- Векторный поиск по каталогу работает, реализация меняется одним конфигом.
- Тест падает, если размерность реализации разошлась с `vector(768)` в схеме.

## T-45. Входное игровое тестирование ⬜

**Ветка:** `onboarding_game` · **Статус:** ⬜ · **Зависит от:** T-44, T-26 · **ТЗ:** 6.4.1

## T-46. Обновление пользовательского эмбеддинга ⬜

## T-48. «Монетка» и пробирование предпочтений ⬜

- Исключения из exploration-пула: скрытые, 18+ без разрешения, «не интересно», просмотренные,

- Параметры (вероятность 15–25%, 2–4 тайтла на подборку) — в конфиге.

**Готово, когда**

# Этап 11. Платные внешние интеграции

Этап начинается, когда весь остальной продукт работает на статике и заглушках.
Каждая задача — замена одной реализации за уже существующим интерфейсом.

## T-74. Реальные клиенты поставщиков ⬜

**Ветка:** `real_provider_clients` (агрегатор) · **Статус:** ⬜ · **Зависит от:** T-15 · **ТЗ:** 6.3.1 · **Решение:** Р-4

Боевой клиент Shikimori GraphQL: тот же запрос и тот же маппер, что и в T-12, — меняется только
источник данных (сеть вместо файла). Плюс авторизация, соблюдение лимитов, курсорная пагинация,
ретраи и обработка ошибок API.

Проверка на расхождение: тест сравнивает структуру реального ответа со статическими фикстурами
и падает, если поставщик изменил схему. Дальше — адаптеры под остальных поставщиков
(AniList/Jikan как источники по аниме, TMDb для фильмов и сериалов) с переводом или
собственным заполнением русских полей. Статический клиент остаётся для тестов и CI.

## T-75. Воркер-агрегатор в бою ⬜

**Ветка:** `aggregator_production` · **Статус:** ⬜ · **Зависит от:** T-74

Вывод агрегатора в прод: расписание обхода нескольких поставщиков, распределение лимитов между ними,
устойчивость к падениям внешних API и деградация без потери данных, backpressure на очереди
доставки в монолит, мониторинг и алерты, разбор dead letter.

Архитектура уже собрана в этапе 1, здесь меняется только источник данных и масштаб —
переносить логику никуда не нужно.

## T-76. Реальная embedding-модель ⬜

**Ветка:** `real_embedding_model` · **Статус:** ⬜ · **Зависит от:** T-44 · **ТЗ:** 7.7

Замена локальной реализации `EmbeddingProvider` на OpenAI `text-embedding-3-small`.

**Состав работ**

- Клиент OpenAI Embeddings с обязательным параметром `dimensions: 768` (Р-5).
  Без него модель вернёт 1536 измерений и запись в `vector(768)` упадёт.
- Пакетная генерация, соблюдение rate limit, ретраи с backoff, таймауты,
  корректная обработка частично неуспешного батча.
- Версия модели сохраняется рядом с вектором: это позволяет пересчитывать выборочно.
- Полная перегенерация эмбеддингов каталога и пользовательских векторов.
- Сравнение качества подборок с локальной реализацией на одной и той же выборке пользователей.
- Оценка стоимости: расход считаем от объёма каталога, пользовательские векторы —
  это среднее векторов тайтлов, отдельных запросов к API не требуют.

**Блокирующий вопрос — доступ из России.** OpenAI блокирует трафик API из неподдерживаемых
стран, включая Россию, с 9 июля 2024 года, а прод по решению Р-9 живёт в Yandex Cloud.
Запросы пойдут с российских IP и будут отклонены. Варианты, которые нужно оценить до старта задачи:

1. **Релей в поддерживаемом регионе** — небольшой прокси-сервис вне РФ, через который идут
   только вызовы эмбеддингов. Генерация и так асинхронная (T-44, T-46), поэтому лишняя задержка
   на UX не влияет. Нужно учесть требования к передаче данных за границу.
2. **Другая модель на 768 измерений**, доступная из РФ: self-hosted `multilingual-e5-base`
   (768 измерений нативно, без внешних вызовов вообще) или эмбеддинги Yandex Cloud —
   у последних нужно проверить размерность, она может не совпасть с 768.
3. **Смена размерности** под выбранную модель — самый дорогой путь: миграция схемы
   и полная перегенерация всех векторов.

Решение принимаем до начала задачи; за интерфейсом `EmbeddingProvider` любой из вариантов
подключается одной реализацией.

## T-77. Платёжный провайдер ⬜

**Ветка:** `real_payment_provider` · **Статус:** ⬜ · **Зависит от:** T-41 · **Решение:** Р-7

Отдельно проверить правила оплаты внутри мобильного приложения для iOS и Android.

не осталось. Ниже — риски, которые нужно снять до соответствующих задач.

| Риск | Когда снимать | Суть и что делать |
| --- | --- | --- |
| **OpenAI недоступен из России** | до T-76, проверить на T-64 | OpenAI блокирует трафик API из неподдерживаемых стран, включая РФ, с 09.07.2024. Прод по Р-9 в Yandex Cloud — запросы пойдут с российских IP. Варианты: релей вне РФ, self-hosted `multilingual-e5-base` (768 нативно), эмбеддинги Yandex Cloud. Подробно расписано в T-76. Дешевле проверить исходящий доступ на этапе настройки прода, чем упереться в него на этапе 11. |
| **Передача данных за границу** | до T-76 | Если выбираем релей к OpenAI, вызовы уносят описания тайтлов за пределы РФ. Персональных данных в них нет (эмбеддинги считаются по каталогу, пользовательские векторы — среднее векторов тайтлов), но соответствие 152-ФЗ подтвердить нужно. Связано с T-58. |
