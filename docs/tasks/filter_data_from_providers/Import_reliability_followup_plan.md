# План доработок оркестратора импорта

Дата: 2026-11-05. Ветка: `3db98b5`.

## Выполнено: конструктор ProviderClientFactory

Фабрика сначала строит карту включённых поставщиков по строковому значению enum.
Повторы удаляются с сохранением порядка первого появления. Копия этой карты
`missing` содержит поставщиков, для которых ещё не найдена регистрация.

Затем фабрика один раз обходит реестр и все фактически указанные источники данных:

1. Проверяет поставщика и нормализует плоскую API-регистрацию во вложенную.
2. Проверяет источник данных, тип имени класса и реализацию ProviderClientContract.
3. Для включённого поставщика проверяет production-запрет mock у каждого обработчика.
4. Запоминает класс по ключу provider + dataSource.
5. Удаляет поставщика из `missing`, если у него есть хотя бы одна валидная регистрация.

Непустая `missing` после обхода означает ошибку конфигурации. Пустой реестр,
отсутствующий ключ и пустой список обработчиков включённого поставщика дают
одинаковую адресную ошибку. Пустые регистрации выключенных поставщиков допустимы;
непустые регистрации проверяются независимо от включения.

Объекты клиентов в конструкторе не создаются. `make()` по-прежнему проверяет
production-запрет при явном запросе выключенного mock. Включённость поставщика
сама по себе не ограничивает явный вызов `make()`.

При E элементах enabled, P поставщиках реестра и R регистрациях стоимость обхода
составляет O(E + P + R), без учёта загрузки классов. Дополнительная память — O(E + R).
Вложенный цикл по поставщикам и их обработчикам сохранён: каждый существующий
обработчик необходимо проверить. Перебор всех ProviderDataSource::cases() удалён.

Проверки фабрики покрывают production-ограничения, неизвестные имена, неверные типы,
отсутствующие и пустые регистрации, дедупликацию, пустой конфиг, плоскую регистрацию,
dump-only поставщика и отсутствие создания клиентов в конструкторе.

Проверено 2026-11-05: все 27 проверок ProviderClientFactoryTest проходят. Связанная
выборка `Import|ProviderClientFactory|Shikimori|AnimeTargetAudienceArrayMigration|CatalogBulkWriter`
содержит 350 тестов: 344 прошли, 6 PostgreSQL-тестов пропущены при SQLite.
Pint для двух изменённых PHP-файлов и git diff --check проходят.

## 1. Корректность обработки ошибок — высокий приоритет

### 1.1. JSON-совместимая диагностика нечислового рейтинга ✅ выполнено

Файлы: ProviderTitleToCandidateMapper, тесты mapper и интеграционные тесты импорта.

- Преобразовать INF, -INF и NAN в строковое представление в контексте отказа.
- Обычные конечные значения вне диапазона сохранять числами.
- Проверить весь путь до сохранения ImportRejection, а не только создание исключения.

Критерий: повреждённый рейтинг даёт один отказ malformed; соседние записи батча,
журнал ID, checkpoint и счётчики успешно сохраняются. Resume не застревает на этой записи.

Выполнено 2026-11-10: ProviderTitleToCandidateMapper пишет INF, -INF и NAN в контекст
строками, конечные значения остаются числами. Без исправления отказ ронял весь прогон
с JsonEncodingException при commit. Тесты: ProviderTitleToCandidateMapperTest
(контекст сериализуется в JSON) и ImportReliabilityTest (отказ сохранён в
import_rejections, соседние записи пачки подтверждены, прогон completed).

### 1.2. Ошибки диагностического логирования после commit ✅ выполнено

Файлы: LogCandidateSink, ImportBatchCommitTest, ImportReliabilityTest.

- Обработать исключения выпуска диагностических сообщений внутри afterCommit callback.
- Предусмотреть, чтобы попытка сообщить об ошибке логирования сама не выбрасывала
  исключение через тот же отказавший logger.
- Не изменять подтверждённый результат импорта из-за недоступности диагностического лога.
- Проверить callback при промежуточном и финальном commit.

Критерий: сбой logger после commit не прерывает оставшийся импорт и не превращает
уже завершённый прогон в ошибку команды. Сообщения об откатившемся батче не выпускаются.
Надёжная доставка обязательных событий остаётся отдельной задачей с transactional outbox.

Выполнено 2026-11-10. Колбэк afterCommit выполняется после PDO commit, но внутри
DB::transaction(): его исключение выходило из recorder->commit(), и подтверждённая
пачка выглядела проваленной. Промежуточный прогон становился failed, а после финальной
пачки команда падала с ошибкой логгера при completed в БД. Теперь LogCandidateSink
не выпускает исключения из колбэка: на первом сбое прекращает выпуск сообщений пачки и
делает одну защищённую попытку Log::warning с числом пропущенных сообщений. Use case
защищает свои Log::error в обработке ошибок, поэтому сбой логгера не подменяет исходное
исключение. Тесты: ImportBatchCommitTest (commit возвращает новый checkpoint),
ImportReliabilityTest (сбой на промежуточном и финальном commit, исходная ошибка при
сломанном логгере); откат пачки по-прежнему ничего не выпускает.

### 1.3. Независимость снимков счётчиков ✅ выполнено

Файлы: ImportTitlesFromProvider, ImportBatch, тестовый recorder.

- Вернуть clone счётчиков при промежуточном commit, сохранив такое же поведение
  на финальной границе.
- Проверить recorder, который сохраняет переданный батч и возвращает его счётчики:
  обработка следующего батча не должна менять ранее переданный снимок.
- Проверить сбой после подтверждённого батча: в БД остаются подтверждённые значения.

Критерий: корректность снимков не зависит от копирования внутри конкретного recorder.

Выполнено 2026-11-10: ImportCounters стал неизменяемым (final readonly,
withAccepted/withFlagged/withRejected возвращают новый снимок), clone в use case
удалены. Снимок пачки или checkpoint нельзя изменить после передачи, независимо от
recorder. Тесты: ImportCountersTest и ImportTitlesFromProviderTest (recorder хранит
полученные пачки без копирования; каждая сохраняет итоги своего commit, итоги
возобновлённого прогона не меняются). Подтверждённые значения после сбоя проверяет
ImportReliabilityTest::it_commits_mapping_rejections_and_resumes_the_remaining_raw_records.

## 4. Явно закрепить поведение на границах

Эти пункты требуют выбора поведения и тестов; они не означают обязательного
изменения текущего контракта.

1. Частичный дамп: документировать импорт подтверждённого префикса. Если требуется
   полный каталог, добавить признак успешного завершения выгрузки и проверять его
   при импорте; предусмотреть совместимость существующих checkpoint-файлов.
2. ✅ Ошибки сырых записей. Клиент отдаёт ProviderTitleRecord с ID, проверенным на
   транспорте; payload разбирается вне генератора. Останавливают источник: транспорт,
   повтор страницы, запись без ID, повреждение дампа, повтор ID в снимке. Mapper
   Shikimori не отклоняет записи: данные неожиданной формы считаются неизвестными,
   а malformed/NO_TITLE решаются в ProviderTitleToCandidateMapper и фильтре.
   Отказ записи подтверждается вместе с её ID, поэтому позиция resume согласована.
3. ✅ Неизвестный kind даёт null-формат и проходит фильтр (ExcludedTitleFormatRuleTest,
   ShikimoriTitleMapperTest); битый kind ведёт себя так же.
4. enabled и явный запуск: документировать текущую разрешающую семантику make().
   Если enabled должен быть запретом запуска, изменить контракт отдельной задачей.
5. API во время изменений каталога: описать отсутствие гарантии полного снимка
   при страничном чтении; при необходимости исследовать поддержку стабильного cursor
   или верхней границы у поставщика.

## 5. Подключение записи каталога — отдельный этап

По умолчанию работает LogCandidateSink. Следующий этап требует сохраняющего sink,
который пишет через то же соединение и транзакцию, что и recorder.

- Обеспечить идемпотентность между разными прогонами и параллельными API/dump-импортами.
- Проверить разрешение идентичности и коллизий, обновления каталога и external_ids.
- Публиковать обязательные задания для медиа и внешние события через outbox.
- Не выполнять HTTP-запросы и обработку изображений внутри транзакции батча.

Критерий: повторный запуск и восстановление после сбоя не создают дубликатов,
а внешние задания появляются только для подтверждённых изменений.
