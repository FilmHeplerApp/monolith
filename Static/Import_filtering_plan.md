# План работ: «Фильтрация данных, полученных от поставщиков»

Рабочий документ задачи. Ветка `645898d`. Документ ведётся по ходу выполнения:
решения фиксируются здесь, этапы отмечаются как выполненные.

Связанные документы:

- [docs/TZ.md](../docs/TZ.md) — разделы 6.3.1–6.3.3, 7.1.2–7.1.8
- [docs/How_infrastructure_works.md](../docs/How_infrastructure_works.md) — слои и правило зависимостей
- `docs/Development_conventions.md` — оформление кода и git flow (в ветке `abstract_provider_clients`)

## 1. Границы задачи

Задача — второе звено из трёх в блоке «Обогащение системы данными» (ТЗ 6.3):

```text
6.3.1 Получение данных от поставщиков   -> ветка abstract_provider_clients (не влита)
6.3.2 ФИЛЬТРАЦИЯ ДАННЫХ                 -> ЭТА ЗАДАЧА
6.3.3 Сохранение отфильтрованных данных -> следующая задача
```

**Вход:** сырые данные провайдера (Shikimori).

**Выход:** одна замкнутая пачка `PreparedCatalogBatch` из четырёх коллекций,
связанных натуральными ключами, и отчёт о прогоне.

```text
1. AttributeDefinition[]        ключ: content_type_code + code
2. AttributeOption[]            ключ: attribute_code + normalize(value_ru)
3. Title[]                      ключ: dedup_key
4. Связи Title -> Definition[]  ключ: dedup_key + attribute_code
```

**Главное требование:** после upsert в задаче 6.3.3 не должно быть дублей,
все связи должны быть корректны. Обеспечивается тем, что пачка физически
не может быть собрана в невалидном виде (см. раздел 4).

**Вне границ задачи (сознательно):** скачивание и сжатие постеров в S3,
генерация эмбеддингов, сам upsert. Фильтрация остаётся CPU-only, без сети и
без записи в БД — за счёт этого она тестируется на фикстурах и работает быстро.

## 2. Источник данных

### 2.1. Отклонённые варианты

**`github.com/Librake/MAL-Parsed` — не подходит.** Проверен полностью: это данные
MyAnimeList, а не Shikimori (постеры на `cdn.myanimelist.net`, имена полей из MAL
API v2, название репозитория `MAL-Parsed`). Кириллица встречается в 1 записи из 4813.

Отсутствуют критичные для ТЗ поля: `title_ru`, любые описания, `status`, `type`.
Под флаг «неполные данные» ушли бы все 4813 записей. Дополнительно:
`episodeDuration` в секундах (у нас минуты), 35 дублей по `titleId` в файле
постеров, 143 тайтла без постера, файлы не сджойнены.

Файлы `Static/anime-list.json` и `Static/anime-posters.json` сейчас в git-индексе —
**убрать из индекса до коммита**, иначе 10 МБ навсегда останутся в истории.

**`pip install anime-parsers-ru` — не нужна.** Это парсеры аниме-плееров
(Kodik, Animego, JutSu); Shikimori там реализован скрапингом HTML. Возвращает
строки из вёрстки (`"вышло"`, `"TV сериал"`) вместо чистых enum-ов официального
API (`released`, `tv`). Плюс отдельный Python-процесс в PHP-монолите.

### 2.2. Принятый вариант: официальный GraphQL API Shikimori

Бесплатный, без ключа и регистрации. Эндпоинт `https://shikimori.io/api/graphql`.

Проверенные на практике ограничения:

| Параметр | Значение | Последствие |
| --- | --- | --- |
| Rate limit | `5 rps` и `90 rpm` | Жёстче — минутный: в среднем не быстрее 1.5 req/s |
| `User-Agent` | **обязателен** | Без него IP банится (прямое предупреждение в документации) |
| `limit` | режется до **50** | Запрос 100 и 200 всё равно возвращает 50 |
| Домен | `shikimori.one` -> 301 -> `shikimori.io` | Бить сразу в `.io` или включать follow-redirects |
| REST vs GraphQL | документация рекомендует GraphQL | REST потребовал бы +1 запрос на тайтл ради описания и жанров |

Объём каталога измерен бинарным поиском границы пагинации: последняя непустая
страница — **479-я**, итого **23 919 записей**. Это реальный размер выборки, а не
лимит глубины: с `kind:"tv"` граница на 173-й странице, с `kind:"ova"` — на 53-й.

### 2.3. Размер дампа (измерено)

Вес записи сильно зависит от выборки: у топа описания длиннее, у хвоста их часто нет.

| Выборка | Б/запись |
| --- | --- |
| топ-250 по популярности | 2739 |
| случайный срез по всему каталогу (300 записей) | **1158** |

Оценки по второй, честной цифре:

| Что дампим | Размер | gzip |
| --- | --- | --- |
| весь каталог (23 919), без `scoresStats` | ~26 МБ | ~7.5 МБ |
| **весь каталог, с `scoresStats`** | **~30–33 МБ** | ~9 МБ |
| только TV (~8 650) | ~9.6 МБ | ~2.7 МБ |

Вклад полей в объём: `description` — 43%, `genres` — 18%, `scoresStats` — 15%.
Остальные 19 полей вместе дают меньше четверти, экономить на них бессмысленно.

## 3. Зафиксированные решения

| № | Решение | Обоснование |
| --- | --- | --- |
| 3.1 | Источник — официальный GraphQL API Shikimori | См. 2.2. Всё нужное приходит одним запросом |
| 3.2 | `scoresStats` дампится **сырым** | Дамп — точный слепок провайдера; свёртка это обработка, её место в маппере |
| 3.3 | `provider_score` / `provider_score_count` — **отдельные поля**; `rating_avg` / `rating_count` импорт не трогает **никогда** | По ТЗ 7.1.2 это рейтинг *наших* пользователей. Иначе ночной импорт затирал бы пользовательские оценки |
| 3.4 | `studios` меняем на `value_type = ARRAY` | Shikimori отдаёт массив: из 250 тайтлов у 13 две студии, у 2 — три |
| 3.5 | Дамп **сырой, без фильтрации на выгрузке** | Иначе в фикстуре не останется краевых случаев, на которых тестируются сами фильтры |
| 3.6 | Формат дампа — **NDJSON**, не JSON-массив | Не держим 26 МБ в памяти; докачиваемость; построчное чтение генератором ложится на `iterable<ProviderTitle>` |
| 3.7 | Идентичность — **гибрид**: `external_ids` авторитетно + `dedup_key` для склейки | См. раздел 4 |
| 3.8 | `dedup_key` присваивается **один раз** и далее неизменен | Переименование тайтла провайдером не должно порождать дубль |
| 3.9 | Жанр **не входит** в `dedup_key` | Жанры меняются между прогонами -> ключ поехал бы -> дубль на upsert |
| 3.10 | Граница с задачей 6.3.3 — интерфейс `CatalogBatchSaver` + DTO | Не сериализованный джоб: пачка не гоняется через Redis, переезд на джоб позже — замена реализации |
| 3.11 | Полный дамп — в `storage/app/import/` под gitignore; в `tests/Fixtures/` — курированный срез 300–500 записей | 26 МБ в git означает новый блоб при каждой перевыгрузке |

## 4. Идентичность сущностей — ядро задачи

### 4.1. Два ключа с разными ролями

| Ключ | Роль | Где живёт |
| --- | --- | --- |
| `(source, external_id)` | **Авторитетная идентичность.** «Это тот же самый тайтл?» | таблица `external_ids`, UNIQUE |
| `dedup_key` | **Технический ключ склейки.** Цель `ON CONFLICT` + схлопывание дублей внутри пачки | колонка `titles`, UNIQUE |

Формула натурального ключа:

```text
natural   = type | release_year | normalize(title_en ?? title_ru)
normalize = lower -> NFKC -> убрать пунктуацию/диакритику -> схлопнуть пробелы -> trim
dedup_key = sha1(natural)
```

Нормализатор версионируется (`NORMALIZER_VERSION`): при его изменении нужен
осознанный бэкфилл, иначе существующие ключи протухнут.

### 4.2. Резолв ключа на пачку — 2 запроса, не N

```text
1. SELECT по (source, external_id) IN (...)  -> нашли? берём УЖЕ ПРИСВОЕННЫЙ dedup_key
2. для оставшихся вычисляем natural key
3. SELECT по dedup_key IN (...)              -> ловим тот же тайтл от другого провайдера
4. что не нашлось — новые тайтлы, ключ остаётся вычисленным
```

Шаг 1 реализует решение 3.8 и чинит проблему переименований.
Шаг 3 — это «поиск возможного дубля по названию, году, типу» из ТЗ 6.3.3,
выполненный пачкой.

### 4.3. Почему ключ обязан быть материализован в БД

1. `ON CONFLICT` работает только по реальному UNIQUE-индексу.
2. **PostgreSQL падает**, если в одном `INSERT ... ON CONFLICT` дважды встретился
   один конфликтующий ключ: `ON CONFLICT DO UPDATE command cannot affect row a
   second time`. То есть дедуп внутри пачки — условие того, что задача 6.3.3
   вообще не упадёт, а не оптимизация.
3. Материализованный ключ решает дедуп между чанками и между параллельными
   воркерами автоматически: второй чанк уходит в ветку UPDATE.

### 4.4. Связи — только пары натуральных ключей

В пачке **нет ни одного числового `id`**. Связь Title -> Definition это
`{titleKey, attributeCode, value}`, а не `{title_id: 42, attribute_id: 7}`.

Порядок применения в задаче 6.3.3 задан топологией, всё в одной транзакции:

```text
1. attribute_definitions -> upsert by (content_type_code, code)  -> map code => attribute_id
2. attribute_options     -> upsert by (attribute_id, value_ru)
3. titles                -> upsert by dedup_key -> SELECT        -> map key => title_id
4. title_attributes      -> upsert by (title_id, attribute_id)
5. external_ids          -> upsert by (source, external_id)
```

**Инвариант замкнутости** проверяется в конструкторе `PreparedCatalogBatch`:
каждый `titleKey` из связей присутствует в коллекции титулов, каждый
`attributeCode` — в коллекции дефиниций. Нарушение -> связь отбрасывается с
причиной на этапе фильтрации, а не падает по FK при сохранении.

### 4.5. Коллизии натурального ключа

Если вычисленный `dedup_key` уже занят тайтлом с **другим** `(source, external_id)` —
это не автоматическая склейка, а кандидат на ручной разбор. Такие случаи идут
в отчёт, а не схлопываются молча (иначе сериал и его рекап того же года сольются
в одну строку, и восстановить это будет нечем).

## 5. Изменения схемы БД

| Изменение | Зачем |
| --- | --- |
| Таблица `external_ids(id, title_id, source, external_id, last_synced_at)`, UNIQUE `(source, external_id)` | Прямое требование ТЗ 6.3.3; авторитетная идентичность |
| `titles.dedup_key varchar(64)` UNIQUE | Без него upsert без дублей невозможен (4.3) |
| `titles.natural_key` (nullable, читаемый) | Отладка и админка; уникальность держит хэш |
| `titles.release_year smallint` | Год нужен в ключе, а колонки сейчас нет |
| `titles.provider_score`, `titles.provider_score_count` | Решение 3.3 |
| `titles.is_incomplete` (или `data_quality`) | ТЗ 6.3.2: неполные сохранять с флагом, а не отбрасывать |
| `titles.last_synced_at` | Требование ТЗ 6.3.3 |
| `import_runs` (+ `import_rejections`) | ТЗ 6.3.3 п.9 и «логировать причины отсева» |
| `attribute_definitions`: UNIQUE `(content_type_code, code)` вместо глобального `code` | Иначе `genres` для аниме и для фильмов не сосуществуют |
| `attribute_definitions`: `studios` -> `value_type = ARRAY` | Решение 3.4 |
| Разрешить противоречие `titles.external_id` | Сейчас это `uuid()` с неуникальным индексом, а `ExternalId` VO требует UUID — при этом id провайдера это `"52991"`. Читаем так: `external_id` это внутренний публичный UUID тайтла, а id провайдеров живут в `external_ids` |

### 5.1. Две ловушки массовых операций

Обе уже обойдены вручную в `database/seeders/TitleAttributeSeeder.php` — учесть
при сборке строк:

- `upsert()` / `insert()` **не поднимают события модели**, значит хук
  `TitleAttribute::booted()->saving()` не сработает и `searchable_text` останется
  пустым. Считать его на этапе фильтрации (логика уже есть в
  `AttributeValue::getSearchableText()`);
- касты тоже не применяются: `value_array` нужно `json_encode` вручную.

## 8. Конвейер фильтрации

```text
iterable<ProviderTitle>
        |
        +- chunk(500)
        |
  ЭТАП 1. Поверхностная валидация      форма, обязательные поля, парсинг enum
          per item, НЕ бросает          -> TitleCandidate | Rejected(reason)
  ЭТАП 2. Нормализация                  BBCode, HTML, обрезка 700-1000, пробелы
  ЭТАП 3. Бизнес-фильтры                accept / flag(incomplete) / reject(reason)
  ЭТАП 4. Резолв ключей                 [2 SELECT на чанк], см. 4.2
  ЭТАП 5. Дедуп внутри чанка + merge    приоритет провайдеров
  ЭТАП 6. Валидация по справочникам     [0 запросов, реестр в памяти]
  ЭТАП 7. Сборка пачки + инвариант      замкнутость связей
        |
        v
  CatalogBatchSaver  +  FilterReport
```

Три принципа:

1. **Ни одна стадия не бросает исключение на битой записи.** Сейчас
   `ProviderTitle` валидирует инварианты в конструкторе и кидает — на пачке
   в 10k одна кривая запись уронит весь прогон. Нужна non-throwing фабрика.
2. **Решение трёхзначное, а не булево.** ТЗ 6.3.2: неполные тайтлы сохраняются
   с флагом, а не отбрасываются.
3. **Никаких HTTP-вызовов внутри фильтрации.** Постеры и эмбеддинги — отдельные
   джобы после сохранения.

## 11. Краевые случаи из реальных данных

Замеры на случайном срезе из 300 записей по всему каталогу (для сравнения:
в топ-250 по популярности все поля заполнены на 100%):

```text
russian      82.0%      english      51.0%
description  46.7%      poster       98.0%
score        63.0%      studios      59.7%
genres      100.0%
```

Чек-лист для курированной фикстуры и тестов:

- [ ] тайтл без `russian` -> отсев (ТЗ: нет ru и en -> отбрасываем)
- [ ] тайтл без `english` -> fallback на `name` (ромадзи)
- [ ] тайтл без `description` -> **флаг неполноты, не отсев**
- [ ] тайтл без `poster` -> флаг неполноты
- [ ] тайтл без `score` -> поведение фильтра по популярности
- [ ] тайтл без `studios` -> связь не создаётся, пачка остаётся замкнутой
- [ ] `kind = pv` и `kind = cm` -> отсев (промо-ролики и реклама)
- [ ] `kind = tv_special`, `ona`, `special` -> решить политику
- [ ] описание с BBCode `[character=...]` -> очистка (117 из 250 в топе)
- [ ] описание длиннее 1000 символов -> обрезка (макс. в выборке 2417)
- [ ] тайтл с 2–3 студиями -> `value_array`
- [ ] `status = ongoing` и `status = anons` -> маппинг в enum
- [ ] тайтл без `airedOn.year` -> поведение `TitleKeyFactory` без года
